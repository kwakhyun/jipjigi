## 먼저 수정할 항목

### 1. [P1] 납부 완료된 청구에도 미납 안내를 접수할 수 있다

- 근거: `apps/web/lib/messaging/service.ts:58–73`, `apps/web/lib/operations/service.ts:85–92`.
- 서버는 청구의 소유권과 수신 동의만 확인하며 `charges.status`를 읽지 않는다. 화면의 대상 목록에서만 `overdue`를 필터링한다.
- 다른 탭에서 입금을 확인한 뒤 기존 메시지 화면에서 접수하거나 API에 납부된 청구 ID를 전달하면 미납 안내 접수 경로로 진입한다. 재접수도 같은 조회 함수를 사용한다.
- 개선: 최초 접수와 재시도 시 청구가 여전히 미납인지 서버에서 검사하고, 상태 변경과 경합하지 않도록 트랜잭션 안에서 검증한다. 대상 상태가 바뀌었다면 명확한 충돌 응답을 주고 목록을 갱신한다.
- 실제 재현: 임시 로컬 데모에서 `status: paid`인 청구 ID로 `/api/operations`에 미납 안내를 요청하자 HTTP 200과 `status: accepted`, `duplicate: false`가 반환됐다. 샌드박스 접수이며 실제 외부 발송은 없다.
- 검증할 조건: 납부 완료, 납부 예정, 미납에서 납부 완료로 바뀐 오래된 화면, 실패 메시지의 재시도.

### 2. [P1] 입금과 수리 변경이 동시 요청 및 부분 실패에 안전하지 않다

- 근거: `apps/web/lib/operations/service.ts:19–35`, `45–75`.
- 상태 조회 후 조건 없이 UPDATE하고 감사 로그와 제품 이벤트를 별도로 저장한다. 두 요청이 같은 이전 상태를 읽으면 둘 다 실제 변경으로 처리될 수 있다.
- 입금 확인에서는 감사 로그와 전환 이벤트가 중복될 수 있다. 수리 완료와 일정 등록이 경합하면 먼저 조회한 상태를 기준으로 나중 UPDATE가 덮어쓸 수 있다. UPDATE 이후 로그 저장이 실패하면 화면에는 실패가 반환되지만 업무 상태는 변경된 상태가 된다.
- 개선: 소유권과 이전 상태를 포함하는 조건부 UPDATE 또는 행 잠금을 사용하고, 변경 행 수로 멱등 결과를 결정한다. 업무 데이터와 감사 로그는 같은 트랜잭션에 저장하고 제품 이벤트는 트랜잭션에 포함하거나 outbox를 사용한다. 트랜잭션만 추가하고 상태 경합을 그대로 두는 것은 충분하지 않다.
- 기존 테스트의 중복 처리는 순차 호출이며 실제 동시 요청과 중간 저장 실패를 검증하지 않는다.
- 확인 수준: 코드 근거의 경합 및 부분 실패 위험. 브라우저에서 두 API 요청을 함께 보낸 한 차례의 시도는 `unchanged: false/true`로 정상 중복 처리됐으며 중복 저장을 재현하지는 못했다.

### 3. [P2] 메시지 멱등 키가 동시 요청의 성공 응답까지 보장하지 않는다

- 근거: `apps/web/lib/messaging/service.ts:148–155`, `204–221`.
- 중복 조회와 INSERT 사이에 다른 요청이 끼어들 수 있다. 두 요청이 모두 기존 행을 찾지 못하면 같은 고유 키로 INSERT하며 하나는 고유 제약 오류가 된다. 고유 키가 중복 행은 막지만, 두 번째 요청을 기존 접수 결과로 반환하지는 않는다.
- 메시지 INSERT, 계약 상태, 전달 타임라인, 감사 로그도 각각 저장한다. 중간 실패 후 다시 요청하면 이미 존재하는 메시지를 반환하는 조기 종료 때문에 누락된 후속 기록이 복구되지 않을 수 있다.
- 개선: `ON CONFLICT` 후 기존 행을 조회하는 흐름과 트랜잭션을 적용한다. 24시간 및 7일 발송 제한의 동시성 검증은 계약 단위로 직렬화한다.
- 확인 수준: 코드의 실행 순서와 DB 제약에 근거한 위험 분석. 별도 DB 재현 테스트는 초기화 시간 초과로 실행되지 않았다. 이후 브라우저의 병렬 API 요청 한 차례에서는 같은 메시지 ID와 `duplicate: false/true`가 반환됐고 경합 오류는 재현하지 못했다.

### 4. [P2] 홈의 주의 건수와 정상 세대 수가 실제보다 적거나 많게 표시된다

- 근거: `apps/web/lib/data/repository.ts:149–188`, `apps/web/components/dashboard/dashboard-view.tsx:74–75`, `124–127`.
- 갱신, 미납, 수리를 각각 `LIMIT 1`로 조회한 대표 카드 수를 전체 주의 건수처럼 표시한다. 정상 세대 수 역시 이 대표 카드에 포함된 호실만 차감한다.
- 예: 미납 호실이 5개여도 미납 카드는 한 건이고, 나머지 4개 호실은 정상 세대 계산에 포함될 수 있다. 설정에 따라 일부 카드를 숨긴 경우는 이미 별도 문구로 처리하지만, 같은 종류의 문제가 여러 건인 경우는 해결하지 못한다.
- 개선: 실제 업무 건수 및 문제가 있는 고유 호실 수와 대표 카드 데이터를 따로 반환한다. 각 카드에 전체 건수와 목록 이동을 제공한다. 집계 전까지는 ‘우선 확인할 항목’처럼 표시 범위를 명시하고 정상 운영을 단정하지 않는다.

### 5. [P2] DB 최초 연결 실패가 해당 프로세스의 후속 요청까지 계속 실패시킨다

- 근거: `apps/web/lib/db/client.ts:163–172`.
- 전역 변수에 DB 생성 Promise를 저장하지만 생성이 실패했을 때 이를 비우지 않는다. 일시적인 연결 또는 초기화 실패 이후에도 모든 요청이 같은 rejected Promise를 받는다. `closeDatabase`도 해당 Promise를 먼저 await하므로 실패 시 정리 구문에 도달하지 못한다.
- 개선: 초기화 실패 시 생성 중 자원을 닫고, 해당 Promise가 여전히 현재 값일 때 전역 참조를 비운다. 재시도 간격과 동시 재접속을 제한한다.
- 확인 수준: 코드 근거. 실제 Neon 장애 주입은 수행하지 않았다.

## 코드 구조와 최적화

### 8. [P2] 홈 조회의 독립 DB 요청이 순차 실행된다

- 근거: `apps/web/lib/data/repository.ts:114–195`.
- 건물 확인, 설정, 입주 현황, 청구월, 수납액, 수리 건수, 갱신, 미납, 수리 대표 항목, 활동을 순차 await한다. 청구월과 수납액처럼 의존하는 관계를 제외하면 상당수는 독립적이다.
- 원격 DB에서는 왕복 지연이 누적된다. 이는 코드에서 확인한 구조적 비용이며 이번 환경의 느린 실행 시간을 그대로 운영 성능 수치로 보지는 않는다.
- 개선: 독립 조회를 제한된 병렬 실행으로 묶고 집계 쿼리를 통합한다. 일관된 스냅샷이 필요하면 트랜잭션 안의 통합 조회를 우선한다. 연결 풀 크기 8을 고려해 무제한 병렬 호출은 피한다.

### 9. [P2] 서버 기동 시 DB 연결과 전체 스키마 변경이 결합되어 있다

- 근거: `apps/web/lib/db/client.ts:159`, `179–395`.
- 새 프로세스가 DB를 처음 사용할 때 전체 CREATE/ALTER와 시드 확인을 실행한다. Neon에서는 전역 advisory lock을 획득한 뒤 실행해 여러 인스턴스의 초기화가 직렬화된다. 마이그레이션 버전을 기록하지만 기록 여부로 실행을 건너뛰지는 않는다.
- 개선: 배포 단계의 버전별 마이그레이션과 런타임 연결을 분리한다. 로컬 편의 초기화는 명시적인 개발 명령으로 남긴다. 다중 인스턴스 배포 시 첫 요청 지연과 잠금 대기를 측정한다.

### 10. [P3] 공통 UI와 데이터 접근 모듈의 책임을 더 명확히 할 수 있다

- `packages/ui/src/index.ts`는 현재 `clsx` 래퍼만 제공한다. 버튼, 배지, 필드, 빈 화면의 실제 규칙은 컴포넌트별 JSX와 689줄 전역 CSS에 흩어져 있다.
- `repository.ts` 하나에 인증 조회, 업무 조회, 설정 변경, 실험 배정, 그로스 집계, 성능 지표가 함께 있다.
- 개선: 먼저 자주 반복되는 Button, StatusBadge, Field, EmptyState와 색상·글자 크기 토큰을 정리한다. 데이터 접근은 업무, 메시지, 실험·관측 영역으로 분리하고 공유 DTO는 서버 repository 밖에서 정의한다. 단순히 파일 개수를 늘리는 분할은 피한다.
- 추가 최적화 후보: 계약 타임라인 전체 조회 후 계약마다 `filter`하는 처리를 그룹별 Map 또는 DB의 행 번호 제한으로 바꾼다. 장부와 메시지 대상 선택에서 필요한 데이터 범위를 줄이고, 실제 데이터가 늘어날 때 서버 페이지네이션과 검색을 적용한다.

## 검증 범위와 결과

- `pnpm verify` 명령은 성공했지만 타입 검사, 테스트, 빌드는 Turbo 캐시를 사용했다. 이번에 새로 126개 테스트가 모두 통과했다는 의미는 아니다.
- 번들 예산 검사: 10개 경로 통과. 홈 177.3/185 KiB, 메시지 168.0/170 KiB. 메시지는 여유가 작지만 예산 초과는 아니다. 번들 크기만으로 실제 LCP/INP가 좋다고 결론 내리지 않는다.
- 캐시 없는 최초 실행: 웹 테스트 파일 23개 통과, 5개 실패. 테스트 107개 통과, 4개 실패, 9개 건너뜀과 워커 기동 오류 3개가 보고됐다. PGlite를 처음 사용하는 테스트와 훅, 워커 응답에서 시간 초과가 발생했다. 공통 패키지의 8개 테스트는 통과했다.
- 최종 웹 테스트: 다른 검증을 마친 뒤 `pnpm exec vitest run --maxWorkers=1`로 다시 실행해 **31개 파일, 126개 테스트 전부 통과**했다. 약 118초가 걸렸다. 따라서 최초 실행의 시간 초과를 기능 회귀로 확정하지 않는다. 테스트 파일과 제한 시간은 변경하지 않았다.
- 실제 E2E는 처음에 로컬 포트 권한 오류, 다음 실행에서는 서버 준비 90초 제한으로 종료됐다. 이후 다른 테스트를 종료하고 단독 실행한 최종 검증에서는 **4개 여정 모두 통과**했다(26.3초). 메시지 접수와 저장 유지, 역할 전환, 방문자 격리, 개인 데모 초기화, 모바일 탐색과 로그아웃을 확인했다.
- 별도 DB 재현 테스트는 초기화 훅의 시간 초과로 실행되지 않았다. 이후 실제 로컬 API에서 납부 완료 청구의 미납 안내 접수는 재현했고, 두 건씩 병렬 요청한 입금과 갱신 접수는 정상 중복 처리됐다. 강제로 동시 조회 시점을 맞추거나 DB 저장 실패를 주입하는 검증은 수행하지 않았다.
- 기존 모바일 캡처와 현재 CSS를 확인하고 색상 대비를 직접 계산했다. 별도로 실행한 임시 로컬 서버에서는 로그인과 393px 모바일 홈 진입, 주요 메뉴 렌더링을 확인했다. 해당 시점의 브라우저 오류 목록은 비어 있었다. 최초 로그인은 장시간 대기했으며 이 환경의 지연을 운영 성능 수치로 일반화하지 않았다.

검토 당시 화면과 명령 출력은 [검증 증거 폴더](2026-09-05-review-evidence/)에 보관했다. 홈 캡처는 브라우저 API로 업무 상태를 변경한 직후 아직 Query를 갱신하지 않은 시점이므로 캡처의 수납 수치를 변경 후 서버 결과로 사용하면 안 된다. 장부 캡처는 입금 확인 후 전체 납부 완료 상태다.

수정 순서는 서버의 대상 상태 검사와 원자적 변경, 홈 집계 정확성, 발송함 상태 안내와 대비 개선, DB 초기화 및 조회 최적화 순서를 제안한다.
