# 운영 데이터의 TanStack Query 적용 결정

변경일: 2026-08-31. 저장소 코드 기준이며 라이브 배포 완료를 뜻하지 않습니다.

## 적용한 곳과 유지한 곳

목록을 `useState`로 관리해도 단일 화면의 성공 결과를 표시할 수는 있습니다. 다만 집지기에서는 같은 계약과 청구를 여러 화면에서 읽고, 웹훅으로도 상태가 바뀝니다. 이 서버 상태를 공유하고 다시 읽는 책임을 Query로 모았습니다.

| 대상 | 결정 | 이유 |
| --- | --- | --- |
| 홈 브리핑 | 기존 Query 유지, 공통 키와 hydration 적용 | 건물별 조회와 다른 화면의 조치 결과 반영 |
| 계약, 장부 | Query 적용 | 메시지 센터의 수신 대상과 같은 원본 공유 |
| 수리 목록 | Query와 mutation 적용 | 일정 및 완료 저장 후 목록과 홈 재조회 |
| 메시지 발송함 | Query와 mutation 적용 | 접수 응답으로 가상 행을 만들지 않고 실제 저장 결과 확인 |
| 미리보기용 알림 설정 | Query 적용 | 설정 저장 후 발송 제한 시간 안내 동기화 |
| 설정 작성 폼 | useState, 네이티브 폼, useTransition 유지 | 재조회로 작성 중인 초안을 덮어쓰지 않음. 저장 성공 후 관련 Query만 갱신 |
| 검색, 필터, 대상 선택, 일정 입력 | 로컬 상태 유지 | 서버가 소유하는 데이터가 아님 |
| 선택 건물 | 홈 내부 Jotai 유지 | 작은 UI 상태이며 서버 DTO와 분리 |
| 공개 페이지, 그로스 관제 | Server Component 유지 | 정적 콘텐츠 또는 조회 전용 집계이며 현재 자동 갱신 요구가 없음 |

## 조회와 캐시 경계

최초 데이터는 Server Component가 DB에서 직접 병렬 조회합니다. 요청별 QueryClient에 넣은 뒤 `dehydrate`와 `HydrationBoundary`로 브라우저에 전달합니다. API를 거치는 서버 내부 왕복이나 최초 렌더 직후의 중복 GET을 만들지 않습니다. 재탐색 시 기존 캐시보다 최신인 SSR 결과도 반영합니다.

브라우저 QueryClient는 `app/app/(management)/layout.tsx`의 임대인 분기에서만 유지하며 사용자 ID가 바뀌면 새로 만듭니다. 홈, 목록과 설정 사이에서는 같은 캐시를 사용합니다. `/app/growth`는 그룹 밖에 있고 URL은 이전과 같습니다. Jotai는 홈 내부에서만 로드되며 홈을 다시 열면 기본 건물로 시작합니다.

- 키: `['owner', userId, resource]`, 브리핑은 건물 ID 추가.
- freshness: 30초. 이 시간이 지났다고 즉시 요청하지는 않으며, 마운트, 포커스 복귀나 연결 복구 시 재조회합니다.
- 브라우저의 사용하지 않는 캐시는 5분 후 정리합니다. 서버 캐시는 요청마다 분리하고 SSR 종료 뒤 GC 타이머를 남기지 않습니다.
- 조회 실패: 네트워크 또는 5xx만 한 번 재시도합니다. 4xx는 재시도하지 않습니다. 화면별 수동 새로고침을 제공합니다.
- 세션 만료, 역할 변경 또는 응답의 소유자 불일치: 기존 목록을 숨기고 로그인을 안내합니다.
- 개인 데모 초기화도 새 사용자 ID와 공급자를 발급합니다. 이전 체험의 계약이나 메시지를 새 공간의 캐시로 재사용하지 않습니다.
- 메시지는 `accepted` 상태가 남아 있는 보이는 탭에서만 15초 간격으로 조회합니다. 오류가 나거나 접수 상태가 없어지면 멈춥니다. 예약 자동 발송이나 실시간 서버 푸시를 구현한 것은 아닙니다.

GET `/api/workspace/[resource]`는 다섯 항목만 허용합니다. 현재 세션의 임대인 역할을 다시 확인하고 클라이언트 입력이 아닌 세션 사용자 ID로만 조회합니다. 계정당 분당 180회 제한과 `Cache-Control: private, no-store`, `Vary: Cookie`를 적용합니다. 브리핑은 기존 `/api/mobile/v1/briefing`을 유지합니다. 모든 Query GET에 취소 신호를 전달합니다.

## 변경 후 무효화

`useOperationMutation`은 기존 Server Action을 호출합니다. 서버의 인증, Zod 검증, 소유권 확인, 멱등 처리와 `revalidatePath`는 그대로 유지합니다.

| 변경 | 무효화할 Query |
| --- | --- |
| 입금 확인 | 장부, 모든 건물 브리핑 |
| 수리 일정 또는 완료 처리 | 수리 목록, 모든 건물 브리핑 |
| 갱신 연락, 미납 안내, 메시지 재접수 | 메시지, 계약, 장부, 모든 건물 브리핑 |
| 알림 설정 저장 성공 | 미리보기 설정, 모든 건물 브리핑 |

활성 Query는 다시 읽고 비활성 Query는 다음 사용 때 다시 읽도록 표시합니다. 재조회까지 변경 버튼의 대기 상태를 유지합니다. 변경 응답을 잃었더라도 일부 저장되었을 수 있어 `onSettled`에서 관련 데이터를 확인합니다. 서버의 저장 시각이나 전달 상태를 브라우저에서 만들어 붙이지 않습니다.

입금과 메시지 변경은 낙관적 업데이트, 자동 재시도, 오프라인 대기열을 사용하지 않습니다. 자동 재조회가 실패하면 이전 목록과 오류를 함께 표시하므로, 저장 성공 안내만으로 최신 조회까지 성공했다고 판단하지 않습니다. 재조회가 일어나기 전까지 다른 탭의 변경을 즉시 알 수는 없습니다.

## 검증과 비용

Query 적용 커밋 `d7eb246`에서는 `pnpm verify`로 웹 27개 파일의 102개 테스트와 공통 패키지 8개 테스트, 5개 패키지 타입 검사, 프로덕션 빌드, 10개 경로 번들 예산을 확인했습니다. 이후 개인 데모 변경의 검증은 [별도 개선 사례](case-studies/demo-reproducibility.md)에 기록합니다.

- 실제 QueryClient를 사용해 동일 목록의 중복 조회 제거, 입금 후 메시지 대상 갱신과 브리핑 무효화를 확인합니다.
- 서버 확인 전 납부 상태를 바꾸지 않는지, 변경 실패가 자동 재실행되지 않는지 검사합니다.
- API 오류 때 기존 목록 유지와 수동 복구, 세션 만료 때 정보 숨김을 검사합니다.
- SSR 데이터 인계, 더 최신인 서버 결과 반영, 계정 전환 시 캐시 분리를 검사합니다.
- 메시지의 접수 응답보다 이후 서버 조회가 반환한 전달 상태를 우선하는지 검사합니다.
- API의 비로그인, 운영자 접근, 항목 허용 목록, 요청 제한과 오류 응답을 검사합니다.
- 별도 임시 PGlite로 연 브라우저에서 홈, 계약 25건, 장부, 메시지 센터, 수리와 설정 폼을 확인했습니다. 계약, 메시지와 수리의 수동 재조회는 정상 응답했고, 임대인에서 그로스 데모로 로그아웃 후 로그인한 화면도 오류 없이 열렸습니다.
- 브라우저의 입금 실행은 안전 검토에서 차단되어 실행하지 않았습니다. 변경 후 동기화는 자동 테스트 범위이며 브라우저에서는 화면 조회와 탐색을 확인합니다.

목록 번들은 적용 전보다 약 13~14KiB 늘었으나 기존 170KiB 예산 안에 있습니다. 홈은 185KiB 예산을 유지합니다. 공개 페이지와 그로스 관제는 이전 번들 크기를 유지했습니다. [경로별 측정값](OBSERVABILITY.md)을 함께 확인하세요. 테스트 수는 이 변경 시점 기준이며 이후 버전 전체의 무결성을 보증하지 않습니다.

설계 참고: [TanStack Query SSR 가이드](https://tanstack.com/query/latest/docs/framework/react/guides/advanced-ssr), [변경 후 무효화](https://tanstack.com/query/latest/docs/framework/react/guides/invalidations-from-mutations).
