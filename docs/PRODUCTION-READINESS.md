# 프로덕션 준비 상태

## 현재 실행 가능한 범위

현재 저장소는 인증된 임대 운영 웹앱의 완결된 세로 단면을 제공합니다. 로그인한 사용자는 건물 브리핑을 보고, 계약 갱신 확인과 미납 안내를 접수하고, 수리 상태와 납부 상태를 변경할 수 있습니다. 각 변경은 Neon Postgres에 저장되고 감사 로그와 제품 이벤트로 이어집니다. 로컬 개발과 테스트는 같은 PostgreSQL 문법을 사용하는 PGlite로 재현합니다.

구현된 운영 경계는 다음과 같습니다.

- 서명된 HTTP 전용 세션 쿠키와 요청별 사용자 재검증
- 브라우저별 개인 데모 작업공간, 역할별 전용 계정과 자기 공간에 한정된 관제
- 한국 날짜 기준 상대 시드, 본인 확인과 동의를 요구하는 초기화, 두 홈 구성 재현
- 건물 소유권과 현재 업무 상태 재검증, 행 잠금과 트랜잭션으로 업무 변경 및 기록의 원자성 보장
- 런타임 연결과 분리한 버전별 마이그레이션, 연결 실패 후 제한된 재접속
- SSR hydration, 계정별 Query 캐시와 변경 영향 범위에 따른 목록 재조회. 조회 오류 재시도와 세션 변경 시 기존 정보 숨김 ([상태 관리 범위](QUERY-STATE.md))
- 임차인 연락 동의, 7일 빈도 제한, 발송 제한 시간의 예약 상태·시각 저장 (자동 처리 미구현)
- 갱신 24시간 제한, 청구월 단위 미납 멱등 처리와 최근 7일 2회 상한
- 전달 실패 재접수, 계약 단위 응답 타임라인과 HMAC 웹훅 검증
- 브라우저·서버 이벤트 분리, 이벤트별 필수 속성 검증, 허용 키 필터링과 서버 확정 실험 문맥
- 사용자 ID 기반 고정 A/B 배정과 실제 노출 기록 분리
- 지역 랜딩 서버 렌더링, 메타데이터, 구조화 데이터, 사이트맵 (현재 빌드에서 정적 HTML 산출은 확인되지 않음)
- 상태 확인 API, 구조화 로그, 독립 오류와 로딩 화면
- Core Web Vitals 수집, 최근 7일 p75 관제, CI 전송량 예산
- CRM 전달률, 전달 후 계약 단위 수신 해제율과 발송 차단률 관제
- Upstash Redis sliding window와 운영 환경 장애 시 차단 우선 처리
- Vercel 운영 환경에서 Neon 또는 Upstash가 빠지면 503을 반환하는 상태 확인

개인 데모는 공개 입장 계정과 실제 데이터 소유자를 분리합니다. 작업공간은 생성 후 12시간이 지나면 인증을 거부하며, 다음 공간 생성 시 만료 공간을 최대 하나 정리합니다. 전체 공간을 50개로 제한하고 활성 공간은 다른 방문자를 위해 지우지 않습니다. 초기화는 현재 공간 삭제와 새 공간 생성을 한 트랜잭션으로 처리합니다. 자세한 경계와 검증은 [데모 재현성 개선 사례](case-studies/demo-reproducibility.md)에 정리했습니다.

## 외부 계약 전에는 켜지 않는 기능

아래 기능은 공급자 계약이나 운영 자격 증명이 없으므로 실제 연동이라고 주장하지 않습니다.

- 카카오 알림톡 실제 발송
- 은행 입금 내역 자동 수집
- 본인인증, 결제, 임대차 신고
- 광고 네트워크와 앱 푸시 공급자

현재 `sandbox_alimtalk` 어댑터가 동일한 메시지 상태 모델을 사용합니다. 실제 공급자는 어댑터를 교체하고 비밀 키를 주입한 뒤 계약 테스트를 통과해야 합니다.

예약 메시지를 시간이 되어도 자동 처리하는 워커는 없습니다. 외부 공급자 없이 접수·예약 저장과 서명 웹훅의 상태 전이만 검증한 범위입니다. 홈, 계약, 장부는 공통 메시지 센터에서 문구를 확인한 뒤 접수하도록 연결되어 있습니다. 홈 알림 설정은 카드 표시를 제어하며 마케팅 동의는 저장만 제공합니다.

## 트래픽 확장 전에 보강할 부분

공유 영속 저장소와 분산 요청 제한은 구현했습니다. 실제 사용자 트래픽을 받기 전에는 다음 운영 기능을 보강해야 합니다.

1. 독립 마이그레이션은 구현했습니다. 다음 단계는 운영과 미리보기 DB 분리, 대용량 이행의 잠금 시간 측정과 롤백 절차입니다.
2. 제품 이벤트와 RUM을 내구성 큐로 보내고 웨어하우스 적재 실패를 재시도합니다.
3. 실제 인증 공급자, 사용자 초대, 비밀번호 재설정과 MFA를 연결합니다.
4. 중앙화된 비밀정보 관리, 로그 수집과 오류 추적을 운영 환경에 연결합니다.
5. 예약 처리 워커, 장애 중 발송 중지 스위치와 복구 후 재처리를 구현합니다. 이 항목은 공급자 교체만으로 완성되지 않습니다.

운영 환경은 `DATABASE_URL`과 Redis REST 인증 정보가 있어야 정상으로 판정됩니다. Redis는 `UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN` 또는 Vercel Marketplace의 `KV_REST_API_URL`/`KV_REST_API_TOKEN` 조합을 인식합니다. 연결이 없거나 응답하지 않으면 요청 제한 대상 작업을 허용하지 않습니다.

## 배포 차단 조건

- `AUTH_SECRET`이 32자 미만이면 프로덕션에서 세션 서명 발급을 거부합니다. 공개 페이지 전체의 시작 차단을 뜻하지 않습니다.
- `ALLOW_DEMO_AUTH=true`가 아니면 프로덕션에서 데모 계정을 만들거나 공개 데모 로그인을 허용하지 않고, 기존 개인 데모 세션도 거부합니다.
- Vercel 운영 환경에 Neon 또는 Upstash 연결이 없으면 `/api/health`가 503을 반환합니다.
- 알림 웹훅 비밀이 없거나 서명이 다르면 요청을 거부합니다.
- GitHub Actions는 타입 검사, 테스트, 프로덕션 빌드, 번들 예산과 실제 웹앱 E2E를 커밋 상태로 검사하도록 구성했습니다. E2E는 임시 로컬 DB에서 실행하며 [현재 실행 검증 상태](E2E.md)를 별도로 기록합니다.
- Vercel 프로젝트 루트는 `apps/web`이며, 배포 빌드는 저장소 루트의 `pnpm verify` 성공 후 `pnpm db:migrate`를 실행합니다. 검사나 마이그레이션이 실패하면 배포를 실패 처리합니다.

E2E는 Vercel 빌드 명령에는 포함하지 않았습니다. GitHub 검사 실패가 자동 배포를 막는 승격 규칙이나 브랜치 보호를 설정했다고 주장하지 않습니다. 공개 제출 전에는 해당 커밋의 E2E 통과와 실제 배포 SHA를 따로 확인해야 합니다.
