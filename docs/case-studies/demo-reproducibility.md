# 평가자가 같은 문제를 다시 볼 수 있는 데모 만들기

작업일: 2026-08-31. 비교 기준: `d7eb246`. 최신 변경의 코드와 로컬 검증 기록이며 배포 완료를 뜻하지 않습니다.

## 문제

기능이 정상 동작하더라도 평가자가 열었을 때 할 일이 이미 사라졌다면 제품의 핵심 가치를 확인하기 어렵습니다. 기존 데모는 모든 방문자가 같은 임대인 계정과 데이터를 사용했습니다. 다른 방문자의 갱신 요청과 수리 완료가 다음 방문자에게 그대로 보이며, 운영자 관제에도 전체 데모 행동이 섞였습니다.

날짜 역시 `2026-08` 청구, `2026-09-27` 만료로 고정되어 있었습니다. 장부 제목은 2026년 8월을 직접 출력했습니다. 시간이 지나면 만료까지 남은 기간과 오늘 접수라는 안내가 실제 데이터에 맞지 않거나 처음 설계한 체험이 사라집니다.

비교 기준 코드는 [기존 로그인](https://github.com/kwakhyun/jipjigi/blob/d7eb246/apps/web/app/login/actions.ts), [기존 시드](https://github.com/kwakhyun/jipjigi/blob/d7eb246/apps/web/lib/db/client.ts), [기존 장부](https://github.com/kwakhyun/jipjigi/blob/d7eb246/apps/web/components/ledger/ledger-view.tsx)에서 확인할 수 있습니다. 이는 코드에서 확인한 재현성 문제이며 실제 방문자의 이탈률을 측정한 결과는 아닙니다.

## 목표와 제약

- 누가 먼저 데모를 사용했는지와 무관하게 핵심 흐름을 확인할 수 있어야 합니다.
- 같은 브라우저에서는 임대인의 조치를 그로스 역할로 이어서 확인할 수 있어야 합니다.
- 두 홈 구성을 명시적으로 다시 시작해 볼 수 있어야 합니다.
- 새 유료 서비스나 운영 전역 초기화 없이 구현해야 합니다.
- 가상 시나리오를 실제 고객의 A/B 성과처럼 표시하지 않아야 합니다.

## 대안과 선택

| 대안 | 장점 | 선택하지 않은 이유 |
| --- | --- | --- |
| 방문할 때 공유 DB 초기화 | 구현이 단순하고 처음 화면을 복원하기 쉬움 | 다른 평가자의 진행 중 작업을 지움 |
| 브라우저 로컬 저장소만 사용 | 서버 비용 없이 격리 가능 | 인증, API, DB 저장과 역할별 집계를 입증하지 못함 |
| 방문자별 DB 인스턴스 생성 | 데이터 분리 경계가 큼 | 데모 규모에 비해 리소스 수와 운영 비용이 큼 |
| 같은 DB에서 전용 계정과 작업공간 생성 | 실제 서버 흐름을 유지하며 데이터 격리 | 정리 정책과 소유권 검증이 필요하지만 기존 owner 범위를 활용할 수 있어 선택 |

## 구현

### 공개 계정과 데이터 소유자를 분리

공개 이메일과 비밀번호는 입장 확인에만 사용합니다. 로그인 후 UUID 작업공간에 전용 임대인과 운영자 계정을 만들고, 그 ID로 세션을 발급합니다. 샘플 데이터는 수정될 수 있는 기존 계정을 복사하지 않고 불변 시드에서 생성합니다.

별도 서명 쿠키가 작업공간을 가리킵니다. 로그아웃은 세션만 지우므로 반대 역할로 다시 로그인하면 같은 공간을 재사용합니다. DAL은 DB의 사용자와 만료 시각을 매 요청 확인합니다. 쿠키 값이나 폼의 임의 ID로 다른 사람의 공간을 선택할 수 없습니다. 이전 공유 계정으로 발급한 세션도 재로그인을 요구합니다.

그로스 역할은 해당 공간 임대인의 이벤트, 메시지와 실험 배정만 집계합니다. RUM은 그 공간의 두 역할을 포함합니다. 실제 계정과 무작위 실험이 아닌 체험 데이터라는 안내를 화면에 표시합니다.

### 날짜가 바뀌어도 같은 과제를 제공

새 공간을 만들 때 `Asia/Seoul` 날짜로 청구월, 만료 28일 전 계약, 5일 전 납부 기한과 최근 수리 요청을 만듭니다. 장부는 실제 청구월을 제목과 집계에 함께 적용하고, 여러 월이 있으면 선택할 수 있습니다. 오늘과 어제는 경과 24시간이 아니라 한국 달력 날짜로 구분합니다.

홈은 실제 청구월을 표시하고 이미 지난 계약에는 `만료 N일 지남`으로 안내합니다. 메시지에도 청구월을 명시합니다. 기존 호환성 테스트의 고정 시드는 남기되 공개 데모 세션에서 그 계정을 사용하지 않습니다.

### 초기화와 자원 한도

체험 설정은 현재 세션과 서명된 작업공간 쿠키의 일치를 확인합니다. 두 안 중 하나를 선택하고 자신의 기록 삭제에 동의해야 합니다. 삭제와 새 시드는 한 트랜잭션에 묶으며 실패하면 기존 공간을 복구합니다. 새 사용자 ID로 시작해 이전 Query 캐시와 실험 노출이 섞이지 않습니다.

공간 유효 시간은 생성 후 12시간, 저장 개수 상한은 50개입니다. 새 생성 시 만료 공간을 최대 하나 지우며 활성 공간은 타인을 위해 삭제하지 않습니다. 로그인과 초기화는 요청 제한을 적용하고 Neon에서는 트랜잭션 생성 잠금으로 상한 경쟁을 막습니다. 초기화 전 동의 문구는 삭제 후 UI 복구가 없다는 점을 설명합니다.

### 실행 중 발견하고 보완한 부분

- PGlite 최초 기동이 테스트 훅의 기본 10초 제한을 넘는 실행이 있었습니다. 해당 통합 테스트의 준비 단계에만 30초 제한을 지정했습니다. 앱 응답 시간이나 번들 예산을 완화하지 않았습니다.
- 숫자 루프백 주소에서는 Playwright의 API 요청이 `Secure` 세션 쿠키를 보내지 않아, 정상 로그인 이후에도 API 검사에서 401이 나왔습니다. 앱과 테스트의 주소를 `localhost`로 맞췄으며 세션 보안 속성을 낮추지 않았습니다.
- 모바일에서 체험 설정 제목이 고정 헤더에 가렸습니다. 해당 섹션의 모바일 `scroll-margin-top`을 조정하고 제목이 헤더 아래에 있는지 E2E로 검사했습니다.
- 화면 이동 직후 이전 설정 화면의 로그아웃 버튼까지 선택하던 테스트는 목적지 제목을 확인한 뒤 계정 바의 버튼을 누르도록 고쳤습니다. 임의 대기 시간이나 자동 재시도는 추가하지 않았습니다.

앞의 테스트 실행 환경 문제와 실제 모바일 화면 문제를 구분해 기록했습니다. 마지막 전체 E2E에서 네 여정 모두 통과했고 수동 브라우저 확인에서도 콘솔 오류가 없었습니다.

## 결과의 의미와 남은 질문

현재 테스트는 다른 방문자의 조치가 자신의 데이터와 관제에 섞이지 않는지, 초기화가 다른 사람의 기록을 지우지 않는지와 달력 변화에도 시나리오가 준비되는지를 확인합니다. 평가자의 과제 성공률이 올랐다거나 체류 시간이 늘었다는 결과는 아직 없습니다.

초기 데이터 두 건물, 27개 호실과 25개 계약은 합성 시나리오입니다. 실제 임대차 운영의 모든 예외를 다루지 않습니다. 공간 상한과 만료 정리는 DB 저장량을 제한하지만 장기 보존, 백업과 대규모 다중 고객 격리를 대체하지 않습니다. 동시성 잠금은 구현했으나 Neon 부하 실험 결과는 없습니다.

다음 검증은 [실제 사용자 관찰 계획](../USER-VALIDATION.md)에 따라 진행합니다. 사람이 핵심 과제를 어디서 오해하는지 관찰한 뒤 변경하고 재검증해야 이 사례가 사용자 중심 개선 증거로 이어집니다.
